## 1. 沿用的产品目标与约束

项目面向缺少现场教练反馈的普通健身用户：自动识别正在做的动作，观察可见姿态偏差，指出部位并给出调整建议，同时提供本人训练记录。识别类别是进入纠错流程的前提，不能只提高分类分数而忽略后续指导。

- 保留当前33个动作与手动备用入口。本轮先补强现有动作，不以扩充数量作为主要成果；不做AI主动澄清或自动追问动作类型，证据不足时显示未知并提供由用户主动打开的手动备用。
- 保留已认可的浅色前端、布局、按钮与动效；如需改善状态提示，使用既有位置，不借此重新设计页面。
- 不从画面推断肌肉实际发力、疼痛、负重公斤数或器械配重片数。
- 当前没有人工教练复核，只有Codex；不能把Codex画面复核或数据集粗good/bad标签写成独立具体错误真值。
- 复用已有素材、特征与通过的检查；只对新增输入、改变的模型及受影响链路补验证。不重复未受影响的高成本测试。
- 外部数据申请、用户语音素材等原有未决事项保留现状；本轮讨论不自动扩大相关授权。

完整业务约定引用[PRD](../PRD.md)、[开发文档](../开发文档.md)与[前端文档](../前端重设计/前端开发文档.md)。当前实现和上一轮证据引用[步骤22末节](../开发步骤/22_常见健身房动作扩展.md#最终候选基础发布与证据)。

## 2. 已核实的起点

当前基础发布已通过，严格逐类及独立姿态错误验收未通过；运行状态保留`full_validation_passed=false`。

### O3-02：各类验证样本和背景负例不足（优先）

八个薄弱动作只有1～5段验证片，讲解负例只有2段；同一原视频多裁切、多时间窗不能算多个独立来源。开发集曾用于选择策略；上一轮已查看的保留片今后只能作为回归材料，不能再次称为全新盲测。

建议按原视频、已知人员及发布者分组检查泄漏，先补弱项的不同人物、器械和机位，再补准备、休息、空手讲解、器械调整、动作中断和不在33类内的动作。多人、遮挡和镜头切换另记输入/拒判表现，不伪造单人正确标签。

### O3-03：分类之后的纠错覆盖仍不均衡（优先）

已验证肩推、划船、硬拉的实际HTTP自动识别→分析→骨架→记录通路，也确认真实俯卧撑缓存能返回部位、建议和高亮。这不能证明33个动作均有足够有效的纠错项，更不能证明纠错准确率。

本轮必须从现有规则与真实片段建立逐动作能力对照：每个动作列出可观察部位、适用机位、实际能检测的偏差、对应建议、骨架高亮、拒判条件和验证等级。2026-10-23只读核查当前33个目录项均标记有参考姿态规则，这不等于33类都具备完整或独立验证过的纠错。优先补用户常练的胸、肩、背与手臂动作；仍需包括原肩推、划船、硬拉的受影响衔接验证。实施时以现有目录/规则生成同一份矩阵，不复制33份重复规格。

看不到关节时返回证据不足；不将“没有检测到问题”显示成“标准动作”。无独立具体错误真值的判项继续标为参考，不承诺虚构的纠错准确率。

### O3-04：首次识别等待及延迟体验（下一优先）

上一轮冷载入约24秒；预热后一次分类中位约1.9～2秒，还要先积累视频窗口。分类推理耗时不等于用户从开始动作到看到结果的总等待时间，也不等于持续姿态反馈延迟。

建议分别记录冷启动、首次确认、换动作确认、姿态提示新鲜度和暂停/结束清理耗时。先检查是否可在合适时机本地预热，再评估资源占用；不能通过保留过期类别/提示来显得更流畅。页面沿用现有提示位置区分“准备模型”“观察动作”“证据不足”，具体是否改动及文案尚待本轮方案确认。

### O3-05：上传视频仍需手动指定动作（已确认纳入）

实时分析默认自动，上传视频分析目前仍按指定动作运行。这是当前功能范围差异，不是前端没有33个动作选项。用户于2026-10-23明确选择本轮一起补齐上传视频自动识别，保留手动备用；这是已确认的新范围，尚未实现。

必须同时讨论多动作视频分段、取消/中断恢复、进度、不同动作记录及原手动兼容，不能只在下拉框增加“自动”而后端仍强制固定动作。复用现有页面，不重新设计视觉风格；是否提供暂停/继续先查现有任务能力，不将尚未实现的控制写成已有按钮。

已确认（2026-10-23）：同一上传视频支持多个动作自动分段，每段分别识别并给建议，不限定为单动作视频。建议流程：选择视频→默认自动模式→后台分析→按源视频时间展示动作段→查看各段反馈；仍保留手动指定动作备用。

以下是围绕已确认功能的处理提案，详细实现及验收仍需补齐：

| 场景 | 建议行为 |
| --- | --- |
| 卧推→休息→弯举 | 两个动作段分别给出类别、时间范围和适用姿态建议；中间休息不计入任一动作 |
| 卧推→休息→再次卧推 | 同名动作仍保留两段；概览可以按类别汇总，但不把两段当两次重复次数 |
| 短暂低置信、遮挡或镜头切换 | 不立即创建一串碎片；待连续证据确认，无法确定的时间保留未知，不能继承上一动作的纠错提示 |
| 静态动作 | 平板支撑等本来就是静态训练，不能因“不动”一律当作休息 |
| 同一人换动作 | 稳定确认新类别后进入对应分析；骨架、判项和建议不跨动作沿用 |
| 从中途开始/结束的动作 | 可以保留有证据的姿态观察；未完成周期不虚增次数 |
| 识别错了 | 已确认支持手动修改所选片段的动作，仅重新分析该段；保留自动原类别与手动类别，不计作自动识别正确，也不自动加入模型训练 |
| 保存与概览 | 一次视频分析任务关联多个片段，片段保留原视频起止时间和来源；重试不重复写记录；统计只使用已确认且支持的检测项 |
| 取消/失败 | 明确已保存部分、未完成部分及失败原因；中断恢复能力按实现确认，不将“重新分析整片”冒充断点续跑 |

单段修正已确认（2026-10-23）；以下为建议交互与实现约束：

1. 在已有片段结果中选择“修改动作”，从当前动作目录选择正确类别，明确本次只影响所选时间段；本轮不默认增加手动拖拽边界的剪辑工具。
2. 提交后显示该段重新分析进度。原自动类别、原结果和修改记录保留；其他段不清空、不重算，也不更改原识别模型。
3. 重新分析成功后生成本段新结果，记录手动指定的动作、源时间范围和规则版本；当前有效统计只使用新结果，不将旧版本与新版本相加。用户修正后的正确类别不作为模型自动识别成功的证据。
4. 重新分析失败、取消或保存失败时保留上一有效结果，明确失败状态；只有新结果保存成功才切换统计。重复点击/重试使用同一请求身份，避免多份有效结果；另一次修改先核对片段版本，避免旧任务覆盖新选择。
5. 原视频临时副本仍可用时复用；已经清理时提示重新选择原文件并核对SHA256和大小。现有`source-match`只核对内容，不提供重新分析输入，需要补接原输入校验/临时副本流程；不永久保留原视频来绕过清理约定。
6. 只对目标片段和必要的模型上下文提取/分析，邻段上下文不进入本段次数和问题统计。无法用原始时间范围精确还原时提示失败，不悄悄换用另一视频或整片结果。
7. 继续使用本人访问权限及账号撤销规则。手动指定只改变动作类别，不代表姿态正确；看不到关节、机位不合适或规则不支持时，仍返回证据不足。

视频上传历史仍遵守既定保留与清理规则，不因自动分段改为永久保存原视频。分析期间骨架与提示必须对应源时间；本轮已纳入用户选择保存的骨架轨迹复盘，新增数据约束见R3-09及开发与验收。旧记录未保存骨架时仍明确不可回放，不回填虚构轨迹；不能把当前只存摘要的实现称为已支持骨架回放。

已核查实现：`VideoJobs`当前按一个`session_id`绑定一个动作，`AutomaticRecorder`当前将来源固定为`camera`。因此上传视频分段不能直接套实时保存器，否则会产生错误来源和时间关联；需补视频任务与片段关系、原视频时间及幂等保存，兼容原有固定动作任务。此处只记录差距，没有修改代码或数据库。

分段验收应单列“动作类别正确”和“边界正确”，使用含换动作/休息/遮挡的连续视频，报告漏段、错段、碎片化和切换延迟。边界容差依据已标注的动作起止与实际采样方案确定；不能以单动作短片分类分数代替整段分段效果。

### O3-06：状态文档存在历史与当前描述交错（已核实）

步骤22开头仍有“新候选未发布”等历史描述，末节和当前模型已是基础发布状态；PRD也保留较早“暂停编码”的历史段落。虽有日期和后续说明，仍容易误读。正式实施时只修正原文件的当前状态入口及历史标识，保留必要证据引用，不重写或复制整套文档。

## 4. 执行顺序

1. 固定当前模型与证据身份，直接分析已有失败片，先定位根因，不先全量重训。
2. 补八个弱项的许可明确真实视频与动作时间边界，单独准备新保留来源；复用其余缓存。
3. 针对根因比较改动：视频输入/时间窗、器械和姿态证据、类别区分、必要的分类层或视频模型微调。先用现有RTX5060 8GB配置可负担的方案；不默认更大的模型一定更好。
4. 对照同一回归集合比较新旧模型，同时用新增来源验证提升，报告各类正确、混淆、拒判与覆盖。
5. 检查核心纠错链的部位、建议、高亮和拒判，补受影响的保存/概览兼容。
6. 按[实施顺序](开发与验收.md#round3-implementation)完善冷启动、上传自动分段/修正、取景/复测/骨架/稳定性、AI、本人档案/负重/导出与手机采集；保持手动备用，功能顺序不表示将已纳入项移出第三轮。
7. 达到约定门槛后更新原需求/开发文档与实际运行模型，保留可用基线；不以训练完成代替发布验收。

### 8.3 调用与数据约束

2026-10-28增量：用户要求画面问答，已增加单次提问的“当前画面”独立授权，默认关闭；可发送少量压缩帧给支持图片的快速解读模型，原图不进入本应用训练库或聊天历史。默认纯摘要流程保持，画面描述与姿态检测分开，详细接口和验证沿用前端开发文档的“AI当前画面问答”节。

1. 本地动作识别、骨架和姿态规则负责产生检测证据；DeepSeek负责解释和组织建议，不覆盖分类结果，不单独创造姿态错误。
2. 按用户最新要求，AI可按需读取更完整的本人训练上下文：档案、目标/器械、相关历史记录与趋势、当前片段全部有效判项/未知原因、用户自填负重/难度、复测/对比及骨架统计特征和批准使用的参考知识。范围由问题和功能确定，可分批检索，不能将“更多信息”实现为一律只给两个简短提示。原视频/相机RGB仍默认本地处理，账号/密钥及无关个人资料不发送；需要外部视觉输入时另外核实提供方能力和授权，不能假装文本接口已看过视频。
3. 仅做去直接标识和按需读取，不宣称完全匿名或提供方零留存。首次使用说明会读取哪些本人数据、哪些内容会发送给DeepSeek；页面可查看本次引用记录/时间范围，并可关闭历史参考。复杂问题允许检索更多相关历史或使用分层摘要，不能遗漏决定结论的反例、未知区间或手动修订。
4. 每条AI结论须引用输入中存在的`evidence_id`/判项及时间，区分“系统观察”“AI解释/建议”“证据不足”；未提供的数值、身体偏差和改善幅度不得补造，不判断实际肌肉发力、诊断伤病或自动规定训练负重。
5. 同一个结果版本可复用已生成的解释；修改动作、规则或当前有效分析后，旧AI解读保留历史身份并标为过期，不用于解释新结果。复用不能跨用户、不同证据或不同提示/模型策略。
6. 调用发生在主动提问或请求复盘时，不按视频每帧调用DeepSeek。AI请求与视觉管线分离，不持预览锁等待网络。
7. 接口输出采用可解析结构并做字段/长度/证据引用校验；JSON格式合法不代表事实正确。空输出、截断或引用不存在证据均不能显示为成功报告，改用明确失败状态与已有规则提示。
8. AI请求有超时、并发及重复点击控制；刷新不自动重复生成，失败不无限重试。网络超时可能已被供应商计费，不保证重试绝不产生额外费用；系统额度模式需另有预算与用量约束。

### 9.2 交互与数据细节

**个人档案**：个人中心新增“训练档案”入口，与昵称/头像/账号安全区分；初学/有经验等经验选项、规范动作/维持训练习惯等目标、常用器械标签、可用时长为用户自述。首版不要求身份证、生日、伤病史或身体照片，不新增必填健康资料。清除档案后AI不再读取旧值，既有分析与报告仍保留生成当时的必要版本标识。

**负重与难度**：在本次结果/片段详情中可填，实时大画面不增加重量仪表盘。保存数值时同时保存单位和“单手/单侧/两侧总计/器械档位/未说明”口径；例如“12.5kg单手”和“第5片”不得互换。空值就是未填，不显示为0kg；难度是主观记录，不等同客观疲劳或错误。AI可结合记录复盘，但不从这些字段自动推定训练负荷安全或完成重量。

**复测**：绑定一个原提示、动作和规则版本，不默认重新检测全项目。用户主动开始/结束；只有计数已开放的动作才按已支持周期给完成量，否则比较可评估时间窗。两段机位/规则不一致或观察不足时不输出“已改善”；原先的错误判断本身缺独立验证时，复测也保持参考等级。

**骨架复盘**：默认关闭“保存本次骨架复盘”，开启前说明保留字段及用途；只保存必要关节坐标、可见性、源时间、画面尺寸/坐标约定和提示关联，不保存RGB/音频。工程默认保留30天，用户可提前删除；到期清理轨迹不删除仍需保留的训练摘要。界面明确到期日，数据量限制和清理结果可见；旧记录无轨迹时显示未保存，不能将插值/重推理冒充当时观测。

**稳定性**：以可比观察窗为单位，覆盖不足或机位/尺度突变时不比较；显示可评估区间，不将无数据时段计为稳定。结果用“后半段左右差异增大”等可支持描述，不能改写成“肌肉疲劳”或“受伤风险”。

**报告**：首版只导出PDF，不无需求地另做多种格式。记录筛选范围、手动修订身份、规则/模型版本、用户填写字段来源、AI报告身份、未知和不完整状态必须可见；无可靠分母不画虚假百分比。默认不含原视频、头像、完整聊天或密钥；服务端和下载均做本人权限核查。生成后过期/删除策略沿项目内文件边界和任务生命周期实现，不建立永久无主导出文件。

**手机浏览器**：用户明确是手机端网页适配，并可直接授权手机相机扫描健身动作；不需要电脑端配对、不把手机变成电脑摄像头，也不新增原生App。可扫码打开站点网址，但二维码不是设备配对或相机授权。手机端保留自己的分析画面、骨架、提示、暂停/继续/结束、上传视频和AI面板；默认只请求视频。手机浏览器采集的图像交由项目后端处理，不宣称4B模型已在手机浏览器端运行。前后摄像头/方向变化需重置流身份和取景；断网、后台或锁屏时停止提交、移除旧骨架/提示，恢复后重新确认，不续接半个动作。移动摄像头需要安全上下文和用户许可；手机访问电脑的局域网IP不属于手机自身localhost，必须准备可达、受信的HTTPS和认证。当前仅本机访问的服务不能写成已可供手机使用，网络前置按实际部署另行落实，本次不擅自开放公网。

## 10. 具体错误识别研究与规则规格（2026-10-28）

用户要求补强握持不当、身体侧倾等明显不标准动作，并研究YOLO与视觉大模型API。本节是待实现、待校准规格，不表示当前软件已经能检测这些错误；标注、训练和发布条件见[开发与验收2.3](开发与验收.md#correction-training)。

### 10.1 当前漏检与技术取舍

本轮核对`gym_catalogue.py`、`gym_motion.py`与`gym_quality.py`：器械推胸主要有躯干摆动和双腕相对肩的高度差两项。躯干判断取窗口内角度P90−P10，因此持续歪着但角度几乎不变时也可能不触发。通路没有手指、拇指与把手关系输入，不能识别具体握法错误。机位过滤还会令判项不可评估；不能通过放开所有机位来修复。

正式分析缓存位于`data/verification/round3/user-demo-analysis.json`的`playlist_review`：新收到6段均未产生确认的姿态问题；用户明确指出1693、1694身体侧倾、握持不当。这个差距仍是开发问题，不把用户说明写成自动检测成功，也不把其他4段自动当作标准动作。

| 组件 | 核实的能力与边界 | 本项目建议 |
| --- | --- | --- |
| YOLO检测/分割 | 提供物体位置或区域；通用权重不保证包含健身器械把手 | 候选检测器械、把手和可握持区；用本场景标注微调，并比较小目标可见性和延迟 |
| YOLO Pose | 默认COCO人体预训练模型是17点；支持自定义关键点与手部任务，不是自带健身错误标签的模型〔S1、S2〕 | 与现有MediaPipe在相同输入比较，不因名称直接替换；默认人体点不能补出手指闭合关系 |
| 手部21点 | MediaPipe输出手指点、左右手和坐标；通用手部数据不是握法正确性标签〔S2、S3〕 | 先试验原分辨率手部局部输入；手被把手遮挡时必须允许未知，不能依赖推测的隐藏手指 |
| 连续规则＋具体错误分类头 | 本项目的新增工程方案，不是预训练骨架现成能力 | 身体侧倾先用可解释几何规则；复杂握法用手、器械关系及有具体标签的时序分类补充 |
| 视觉大模型API | 支持图文理解；细粒度健身质量判断、错误定位仍有局限〔S4、S5〕 | 复用已有视觉接口，作为主动触发或已授权的低频疑难复核；单列复核来源，不静默覆盖本地判项 |

建议通路：确认动作/变式 → 同人身体与手部跟踪 → 器械/把手关联 → 分阶段几何证据＋具体错误分类 → 持续确认/拒判 → 部位提示。握法依赖手与器械关系，不能仅训练整帧“好/坏”二分类。

现有聊天附图与连续纠错是不同通路。复核若实施，应从原始分辨率提取同一时刻的全身图与手部局部图，保留源时间；不能先缩小全身再放大手。DeepSeek文档说明`detail:low`会将输入缩至512×512〔S4〕；局部输入是否改善本项目握法仍需真实对照。私人演示原片原有不上传第三方约定继续有效。

### 10.2 共用观察条件与测量约定

以下16项均是候选规格。P0优先处理1693/1694相关问题及当前漏检，P1随后补齐；优先级不代表已发布。

- 每项绑定`action_id + variant + equipment_template`、源时间和解剖侧别。没有匹配变式时不可评估；正握、对握、反握、单侧、交替、离背等合法变式不能一概判错。ACE推胸指导也包含单侧和离背变式〔S6〕。
- 二维点先还原像素宽高比、裁剪和旋转。竖直方向须来自核实的相机方向/器械轴，不以歪斜图像边缘当重力。身体和手部世界坐标不能未经配准直接拼接；优先用同帧图像坐标及局部到全图变换。
- 肩中点记S、髋中点H、躯干投影长L；距离以适用的L、前臂长或器械局部尺度归一化。比例分母过小、离面旋转明显、遮挡/模糊、镜头移动、身份变化或时间不连续时拒判，不用插值补造检测证据。
- 各项独立标定偏差阈值θ、连续触发T_on、恢复阈值及T_off、最小有效覆盖C_min。“持续”指连续有效源时间超过该项T_on，“重复”指完整有效周期再次出现；不跨遮挡拼接。具体数值待标定，动作教学不是任意角度门槛的科学证明。
- 侧倾保留绝对偏离和符号，不能用摆幅代替；动态项保留动作阶段与速度，不能只看一帧宣布失控。初始姿势可能已经错误，不自动将前几秒当标准基线。
- 只描述可见投影偏差，不推断握力、实际受力、疼痛、重量或伤病。未检出不等于整体标准。同时间重叠判项只突出一个主要建议，其余保留在详情，避免提示堆积。

| E12 `abrupt_return` / P1 | 要求受控回程的推胸/弯举等；主运动平面；源时间、连续把手/腕轨迹 | 完整回程时长、归一化速度突变及端点反向轨迹共同异常并重复；描述急促，不直接断言失控 | 爆发专项/快速变式、视频变速、时间不可靠、镜头震动、轨迹跳点 | “回程较急，尝试缓慢控制返回。”〔S6、S8；无通用秒数阈值〕 |
| E14 `support_hip_alignment` / P1 | 标准平板支撑/俯卧撑分阶段模板；侧面；肩髋踝，跪姿另用膝支点 | 髋相对肩—踝连线的有符号距离/L持续超θ，区分抬髋/下沉；俯卧撑分上下阶段 | 派克/登山等折髋变式、跪姿未匹配、斜机位、支点不可见 | “髋部持续{偏高/下沉}，尝试恢复稳定连线。”〔S7；不能推断腰椎局部曲度〕 |
| E15 `medial_knee_shift` / P1 | 常规双脚深蹲；近正面；髋膝踝及足向 | 下降/起身膝相对同侧髋足轨迹向内偏移及动态变化超θ，保留侧别并重复；不设统一膝距 | 足向不可见、镜头偏斜、交叉/单腿动作、仅静态腿型差异 | “{侧}膝在动作中明显内移，检查是否沿脚的方向移动。”〔S9；不诊断伤病〕 |
| E16 `heel_lift` / P1 | 要求全脚支撑的常规深蹲；侧面/斜后；足跟足尖、鞋底、地面 | 足跟相对地面抬起且足尖仍支撑，距离按足部尺度归一化并持续 | 鞋跟结构、垫高脚跟、跳跃/踮脚变式、地面不可见；骨架单点抖动不足 | “{侧}脚跟离地，先恢复稳定支撑再继续。”〔S9〕 |

不加入“膝盖过脚尖必错”“所有推胸都必须正握”“肩线稍斜必错”等一刀切规则；深蹲需按动作方式及个体条件判断〔S10〕。16项不等于33动作完整覆盖，未匹配动作继续保留覆盖缺口。

### 10.6 资料依据与边界

以下为2026-10-28核对的一手文档/原作者论文。动作指导支持规范方向，不能证明本项目阈值、准确率或所有器械适用性；表中工程推导均需实测。

- S1：Ultralytics，[Pose Estimation](https://docs.ultralytics.com/tasks/pose/)，默认COCO人体点、自定义任务及训练。
- S2：Ultralytics，[Hand Keypoints](https://docs.ultralytics.com/datasets/pose/hand-keypoints/)，21点标注来自MediaPipe，不是握法错误标签；使用前另核对许可。
- S3：Google，[Hand Landmarker](https://ai.google.dev/edge/mediapipe/solutions/vision/hand_landmarker)，手部点、左右手与坐标。
- S4：DeepSeek，[Vision](https://api-docs.deepseek.com/guides/vision/)，图文接口及图像细节处理。
- S5：Zheng等，[FitAQA原论文](https://arxiv.org/html/2608.08736v1)，可见错误、多标签和时间定位评测；局限节明确不覆盖器械握持错误，不能直接验收本项目握法。
- S6：ACE，[Seated Chest Press](https://www.acefitness.org/resources/everyone/exercise-library/188/seated-chest-press/)，闭合握持、腕与前臂方向、坐姿、受控返回及合法变式。
- S7：NASM，[Plank](https://www.nasm.org/resource-center/exercise-library/plank)，稳定连线及髋下沉；俯卧撑各阶段与跪姿仍需单独模板核对。
- S8：NASM，[Barbell Bicep Curl](https://www.nasm.org/resource-center/exercise-library/barbell-bicep-curl)，肘位置、摆动及受控回程；不把特定握距或训练量直接设为通用硬规则。
- S9：ACE，[Bodyweight Squat](https://www.acefitness.org/resources/everyone/exercise-library/135/bodyweight-squat/)，膝足方向与脚跟支撑；不把全部教学细节套给其他蹲法。
- S10：NASM，[The Biomechanics of the Squat](https://www.nasm.org/resource-center/blog/training/biomechanics-of-the-squat)，站距、足向、个体差异与可控制深度；不据此添加统一膝尖位置或蹲深门槛。

## 11. 开源实现参考、训练必要性与共同标注（2026-10-28）

用户补充要求：第三轮以真实纠错可用为主；可采用YOLO和视觉大模型API；如需标注，希望由Codex与用户共同完成，而非让用户自行学会训练格式。仍先完善文档，后续再实施。本节选型不承诺单个模型能解决所有错误；成功按真实可见错误检出、正常/合法变式误报、证据不足处理和既有验收指标判断。

### 11.1 查阅开源项目实际怎么做

| 项目与查阅位置 | 实际方法 | 本项目采用的思路与限制 |
| --- | --- | --- |
| LearnOpenCV，[AI Fitness Trainer](https://github.com/spmallick/learnopencv/tree/master/AI-Fitness-Trainer-Using-MediaPipe-Analyzing-Squats)；查阅`process_frame.py`、`thresholds.py`及其[原教程](https://learnopencv.com/ai-fitness-trainer-using-mediapipe/) | MediaPipe关键点 → 角度/机位条件 → 深蹲阶段状态机 → 当次反馈与正确/错误计次；不同配置给出固定阈值，纠错主体是规则，不是另行训练通用错误网络 | 借鉴连续阶段、周期结束汇总、错误持续和状态重置。其动作、机位和阈值很具体，不能原样推广到推胸、握法或33类；尤其不照搬统一膝尖位置等规则 |
| Ultralytics，[AIGym源代码与参考](https://docs.ultralytics.com/reference/solutions/ai_gym/) | 从姿态关键点索引计算目标角度，使用`up_angle/down_angle`、stage与计数状态判断动作往返 | 可参考YOLO姿态推理、角度平滑和计次接线；该类的主要输出是角度/阶段/次数，不能当作已训练的常见错误库，更没有开箱即用的握法纠错 |

结论是复用“预训练视觉提取＋动作阶段＋专用规则/错误分类”的组织方式，不把下载一个健身演示项目当成纠错已完成。代码或权重复用前按实际版本核对许可；本次只读研究，未克隆项目、安装依赖或下载模型。

### 11.2 推荐落地组合

1. 保留现有动作分类器作为入口；不再把重复训练动作名称分类当成本轮主要进度。侧倾、前后摆动、双侧同步先复用已有身体关键点，修测量与机位逻辑。
2. 在同一视频源时间加入手部局部识别。只有身体关键点确有明显不足时，才通过对照决定是否换YOLO Pose；把手/握持区检测另作为YOLO候选任务，不能指望人体Pose同时理解握法。
3. 将16项规则按实际变式逐项接入：先身体侧倾及已有判项，再检查手部清晰度、折腕、握持位置，随后补握向/闭合关系和时序项。没有足够输入的项保持不可评估，不挂空能力。
4. 对规则难以稳定区分的具体握法错误，用手部局部视觉、器械关系及连续阶段训练多标签分类头；先证明每种输入的增益，不从零训练整套大模型。
5. DeepSeek视觉API先作为主动复核通路，输入同源全身、手部局部及必要前后帧，关联明确时间。只有经过真实错误/正常/遮挡对照并满足对应指标，才讨论将其加入自动纠错；不逐帧调用，也不将流畅解释当检测正确。

### 11.3 哪些需要标注

| 任务 | 是否需要自己标注 | 用户实际需要做什么 |
| --- | --- | --- |
| 直接使用预训练身体/手部模型 | 初次使用无需重标所有人体/手指点；仍需检查本场景是否可靠 | 看提取结果是否对应本人、关节或手是否明显跑偏，不必逐帧点33点/21点 |
| 手写侧倾、摆动、同步等规则 | 不需要先训练权重，但需标注正常、具体错误和未知片段来校准/验证 | 选择问题、左右侧和起止时间；正常只表示已经检查的判项未见问题 |
| 微调YOLO识别器械把手/握持区 | 需要目标框/区域标签；人体框数据不能代替把手标签 | 在少量关键帧核对/调整预标框；自动传播后再抽查，不从头逐帧画满整段。YOLO格式由Codex导出，不让用户填坐标〔S11〕 |
| 训练具体握法错误分类 | 需要对应错误的时间段/局部样本标签、正常反例及不可见样本 | 看局部短片，选“折腕/握向不符/位置不一致”等可见项，模糊或不确定就选“看不清/待讨论” |
| 视觉API直接推理 | 调用已有模型不需要先给供应商训练数据；可靠性评估仍需人工标签 | 核对它指出的时间和部位是否真实，错误建议和漏检也记录；本项目不默认将私人素材上传作训练 |

S11：Ultralytics官方[目标检测数据格式](https://docs.ultralytics.com/datasets/detect/)。框和分类标签的区别需保留，不能只有“该视频握错了”就直接训练把手检测器。

### 11.4 用户与Codex怎样一起标注

后续优先在项目现有本地视频能力上增加轻量标注入口，不先安装一整套CVAT/Label Studio；本轮仅定义流程，入口尚未实现。素材继续留在项目受控目录，原片只读，保存标签和引用，不反复复制视频。

1. Codex先整理现有6段视频及可见区域，提出5～10个短区间作为试标材料；这是熟悉流程的小批次，不是足够训练或验收的数据量。
2. 页面播放原短片，可暂停、慢放，并同时看全身和同源手部局部。用户先确认动作/变式；不清楚的器械握法先讨论，不强制猜选。
3. 用户按实际可见情况选“发现问题”“所查项目未见问题”或“看不清/不确定”。“所查项目未见问题”只针对当前已检查的错误码，不能代表全部16项正常。
4. 发现问题时勾选一个或多个错误、左右侧；拖动或点选问题开始/结束位置。Codex负责源时间映射、规则码、数据格式及完整性校验。
5. 算法可以预先建议区间或框，但显示为待确认；用户不确认的预标不直接混入人工标签。Codex解释每个选项，双方对不清楚的样本保留待讨论，不强行凑正常/错误。
6. 只有检测把手确需微调时，才增加关键帧画框任务：用户框出把手/握持区、检查预标边界，Codex处理跟踪传播与训练格式。先演示少量样本，确认理解一致后再扩大。
7. Codex完成去重、来源分组、训练/开发/独立保留划分、候选训练和对照。用户只需要看视频判断，不负责命令行、目录、坐标文件或模型参数。
8. 每轮呈现命中、漏检、误报的实际区间，优先让用户复核分歧样本并修正标签；模型候选有证据优于旧版才发布。已用于调试的1693/1694始终只算开发回归，不变成独立验收片。

示例操作仅用于解释：若某试标片在第4～7秒可见向本人左侧倾斜，就选择“身体侧倾—左侧”，标开始4秒、结束7秒；同段握法看不清则将握法标未知，不顺带判正确。该例不表示现有某段视频已经完成该时间标注。

用户确认与Codex辅助标注应保留各自来源，不冒充独立教练审核。可以先完成工程纠错与开发回归；动作规范有争议的具体项在依据和复核不足时保留未验收，不凭双方猜测宣布专业准确性。

### 11.5 API申请与项目配置

优先使用项目已经接线的DeepSeek视觉接口，不要求现在同时申请多个平台。官方[调用说明](https://api-docs.deepseek.com/)和[视觉文档](https://api-docs.deepseek.com/guides/vision/)于2026-10-28核对：当前图文模型为`deepseek-flash`。其他供应商只有在相同授权样本对照显示必要收益时再评估；密钥不可跨供应商混用。

以下由用户在自己的账号操作，代码实施阶段再进行真实图像验证：

1. 打开官方平台`https://platform.deepseek.com/`，登录或注册自己的账号。
2. 打开官方密钥页`https://platform.deepseek.com/api_keys`，进入“API keys”，选择创建新密钥入口（`Create new API key`；界面显示文案可能随语言调整）。
3. 如需填写密钥名称，填`fitness-assistant`，确认创建后复制密钥；将真实值只填入本项目的密码输入框，不发在聊天或写进文档。
4. 在平台确认账号可用余额/额度；若不足，由用户按控制台可选金额补充小额测试预算。本步骤没有代用户充值或实际调用授权。
5. 项目启动后，打开当前健身站点，点击头像 → “设置” → “AI 服务”下的“密钥与偏好”；当前本机预览地址可直接打开`http://127.0.0.1:8765/account/ai`。若站点使用其他已启动地址，则在该站点走同一菜单，不新建空库替代当前账号。
6. “调用来源”选“个人DeepSeek密钥”；“解读方式”选“快速解读（支持看图）”；在“个人API密钥”粘贴刚创建的Key，点击“保存设置”。无需另填API地址，现有服务端使用官方地址。
7. 点击“测试连接”，应看到“连接成功”，设置状态为“已配置”。当前测试只核对连接/模型可访问，不能据此说真实看图或纠错已通过。
8. 完成后只回复“密钥已配置，连接成功”，不要发送Key。后续确认测试预算和允许发送的样本范围，再实际验证全身/局部图、正常/错误/未知及费用；原演示视频禁止第三方上传的约定继续有效，须用获得对应许可的测试材料。

API配置不等于第三轮纠错完成。第三轮继续以[开发与验收9.2](开发与验收.md#92-纠错效果)和实际错误视频为准；模型启动、API连通、规则数量、聊天能描述画面分别记录，不互相替代。

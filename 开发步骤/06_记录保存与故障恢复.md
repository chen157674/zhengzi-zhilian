## 保存边界与故障注入顺序

| 场景 | 本步可独立验证的输入 → 结果 |
| --- | --- |
| 正常／重复提交 | 已知事件序号 1、2 及同一静态区间多次提交 → 两个事件，区间只累计一次，摘要与明细一致 |
| 事务未提交即失败 | 事件写入后摘要更新前抛出受控故障 → 整批回滚，重试同批次后只出现一份 |
| 已提交但响应丢失 | 返回前模拟连接失败 → 查询原回执／版本，识别已成功，不新建会话或再加次数 |
| 持续无法写入 | 冻结待提交批次 → 取消放弃仍保留内存；明确确认后仅丢该批未提交数据，旧摘要不删除，终态无法落库须说明 |
| 归属／删除冲突 | 混入别人的／活动中的／旧版本记录 → 整批零删除；没有一条成功后再校验下一条 |

本步验证仓储事务、故障状态、历史／确认框；08 接续真实采集冻结与控制释放，10 接续解码任务停止与临时副本，12／14 接续真实运动事件汇总。先检查数据库最终行数／版本与实际 HTTP 返回，再检查页面，不能只看 toast。故障注入只在本任务测试库／测试依赖中，不修改真实记录或填满用户磁盘。

## 实际实现与验证（2026-10-19）

- `fitness_app/records.py`：服务端事件／区间事务、同序号去重、静态区间并集及原因保留、组状态与摘要一致；历史按实际开始时间和 ID 稳定倒序。未开始和演示不进入个人列表；API 不接受客户端自报次数／评估。
- `fitness_app/persistence.py`：首次保存失败即发出冻结信号，只保留一个不可变原批次；自动在约 0.5／1.5／3.5 秒重试，之后保留手动处理。先核提交回执解决响应不确定；成功后不会自动继续运动。确认放弃使用有界进程回执，存储仍不可写时不循环阻塞退出，并显式返回 `terminal_persisted=false`。真实采集／解码冻结与原控制身份在数据库完全不可读时的收尾交 08／10。
